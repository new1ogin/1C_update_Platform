# CONTRIBUTING.md

Краткие правила по доработке проекта **1C_update_Platform**.

## Общие принципы

1. **Сначала читаем код.** Перед любым изменением откройте соответствующий `.au3` и убедитесь, что понимаете
   алгоритм. Подробное описание обоих скриптов с указанием функций и регулярных выражений — в `README.md`,
   разделы «Ключевые файлы» и «Пример сценария работы».
2. **Меняем только логику, не нарушая существующее поведение.** Обе программы рассчитаны на постоянную работу
   через планировщик: они должны безопасно завершаться, если делать нечего. Не добавляйте модальных окон,
   `MsgBox`, `ShellExecute` и всего, что может заблокировать незакреплённый сеанс.
3. **Не выдумываем.** Если для изменения не хватает данных (поведение на вашей версии платформы, состав
   конфигурации веб-сервера и т. п.) — помечаем это в описании изменений как «не указано» и не предполагаем.

## Где что менять

| Нужно изменить | Файл | Замечание |
|---|---|---|
| Логику восстановления `techsys.dll`, обработку служб сервера 1С | `1C_update_Platform.au3` | |
| Логику перепубликации Apache/IIS | `1C_Web_update_Publication.au3` | |
| Интервалы запуска, учётную запись задания | `Планировщик-*.bat` | |
| Сторонние UDF | `Include\` | Только если точно понимаете последствия; по возможности UDF не трогаем |

**Важный нюанс.** Планировщик запускает не исходный `.au3`, а `*_stripped.au3`, а `.ini`-файлы формируются по
имени запущенного скрипта. Поэтому после любого изменения `.au3` нужно пересобрать `*_stripped.au3` и, при
необходимости, `.exe` (см. `README.md`, раздел «Сборка проекта в EXE»). Не правьте `*_stripped.au3` вручную —
этот файл генерируется Au3Stripper'ом и будет перезаписан.

## Стиль кода

- Сохраняем сложившийся стиль: табуляция для отступов, префиксное именование функций с ведущего подчёркивания
  (`_getLastPlatform64`, `_getApachePublication`), кириллические комментарии.
- Исходные файлы хранятся в кодировке **Windows-1251** (как и существующие `.au3`). При пересохранении следите,
  чтобы редактор не переключил файл на UTF-8, иначе кириллические комментарии превратятся в «кракозябры».
- В `bat`-файлах используется `chcp 1251` — это нужно сохранить.
- Сообщения журнала (`_log`) пишем на русском, в том же формате: `<дата_время>\t<компьютер>\t<сообщение>`.
- Любое изменение логики сопровождаем комментарием о том, что именно и зачем делается.

## Проверка изменений

1. Запустите изменённый скрипт вручную из консоли и просмотрите вывод `ConsoleWrite('@@ Debug …')`:
   ```bat
   AutoIt3.exe "1C_update_Platform_stripped.au3"
   ```
2. Проверьте журнал `<имя скрипта>.log` рядом со скриптом — там должны появиться ожидаемые сообщения.
3. Прогоните скрипт **дважды**: второй запуск не должен повторно вносить изменения (защита от дубликатов в
   `_log()` и проверки «уже стоит новая версия» / `$succ`).
4. Проверьте сценарий «нет новых платформ» — программа должна тихо завершиться, не тронув файлы и службы.
5. Для веб-скрипта дополнительно проверьте сценарий «DLL новой версии не существует» — правка конфигурации
   должна быть отменена.
6. Убедитесь, что после ваших изменений не осталось временных файлов: `*.tmp`, `*.log`, `*.ini` и `*.7z` в
   Git не попадают (см. `.gitignore`).

## Оформление изменений и коммитов

- Сообщение коммита — на русском, короткое и в повелительном наклонении
  (например: `Добавить проверку существования DLL перед перепубликацией`).
- Не коммитьте `.ini`-файлы с PID, `.log`, `OAER_RAW_SRC.tmp`, `*.7z` и `opencode.json` — они уже в `.gitignore`.
- Если меняется поведение, доступное пользователю, — обновите `CHANGELOG.md` по схеме
  [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/), раздел «Несортированное» или новый
  `Added`/`Changed`/`Fixed` под новой версией.
- Если меняется состав файлов, назначение компонентов или системные требования — одновременно обновите
  `README.md` (разделы «Структура проекта», «Компоненты проекта», «Системные требования»).

## Безопасность при доработке

- **Никогда не коммитьте секреты:** пароли, токены, строки подключения, имена пользователей и личные пути.
  Все подобные значения — только через переменные и примеры вида `<пример>`.
- Учитывайте, что программы работают с правами администратора (`#RequireAdmin`): любой новый вызов
  `RunWait(@ComSpec …)`, `RegWrite`, `FileDelete` и `FileWrite` должен быть явно обоснован.
- Не добавляйте отправку данных во внешние сервисы, не описав это в `README.md` в разделе «Безопасность и
  обрабатываемые данные».

## Вопросы и сообщения о проблемах

При сообщении о поведении программы прикладывайте: версию платформы 1С, список установленных версий в
`C:\Program Files\1cv8`, используемый веб-сервер и фрагмент журнала `<имя скрипта>.log`. Персональные данные
из журнала (имена компьютеров, пути) можно замаскировать.
