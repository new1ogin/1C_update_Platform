# 1C_update_Platform

**Набор скриптов на AutoIt, которые автоматически «доводят» сервер 1С:Предприятие после обновления платформы.**

Проект состоит из двух независимых программ, которые по расписанию определяют, что на сервере появилась новая
версия платформы 1С, и выполняют типовые действия, которые иначе приходится повторять вручную после каждого
обновления. Обе программы рассчитаны на постоянную работу через планировщик заданий Windows. Графического
интерфейса у них нет — окон и диалогов не появляется, а результат пишется в журнальный файл рядом со скриптом.

## Коротко для нового читателя

| Вопрос | Ответ |
|---|---|
| **С чего начать?** | Запустите от имени администратора один из файлов `Планировщик-*.bat` — он зарегистрирует задание в планировщике Windows. Подробности: «Установка и запуск». |
| **Что произойдёт?** | `1C_update_Platform` перенесёт ваш `techsys.dll` в новую версию платформы; `1C_Web_update_Publication` переключит на новую версию публикации Apache/IIS и перезапустит веб-сервер. |
| **Где результат?** | В журналах `1C_update_Platform.log` и `1C_Web_update_Publication.log` рядом со скриптами. |
| **Это безопасно?** | Программы работают с правами администратора и меняют файлы в `C:\Program Files`, конфиги веб-сервера, реестр и состав служб. Сначала проверьте на тестовом сервере — см. «Безопасность и обрабатываемые данные». |

**Что такое `techsys.dll`.** Это файл платформы 1С из каталога `<версия>\bin`. В самом проекте этого файла нет —
программа его не распространит и не изменит. Она лишь повторяет для новой версии платформы то, что вы ранее
сделали в предыдущей: берёт `techsys.dll` из прежней установки и переносит его в новую.

## Описание

- **`1C_update_Platform`** — восстанавливает файл `techsys.dll` из прошлой версии платформы после установки новой.
  Самого файла `techsys.dll` в репозитории нет: программа не хранит «эталон», а лишь повторяет те изменения,
  которые вы ранее сделали в прошлой версии платформы — берёт `techsys.dll` из прежней установки и переносит его в
  новую. Дополнительно программа перезапускает службу сервера 1С, если та уже работает на новой версии.
- **`1C_Web_update_Publication`** — перепубликует базы на веб-сервере (Apache, а также IIS) на новую версию
  платформы и перезапускает веб-сервер.

## Какую проблему решает проект

После каждого обновления платформы 1С на сервере приходится вручную выполнять одни и те же действия:
заново накладывать модификацию `techsys.dll` (иначе настройки/доработки платформы, сделанные ранее, теряются),
править конфигурацию веб-сервера так, чтобы опубликованные базы заработали на новой версии платформы, и
перезапускать службы. Забыл хотя бы один шаг — базы перестают открываться или работают «на старой» платформе.

Проект делает эти операции автоматически, поэтому скрипты можно держать запущенными по расписанию постоянно:

- `1C_Web_update_Publication` идемпотентен: после перепубликации при следующем запуске он видит, что в
  конфигурации уже стоит новая версия, пишет «Уже стоит новая версия» и завершается без изменений.
- `1C_update_Platform` на каждом запуске повторяет перенос `techsys.dll` заново. Состав файлов от этого не
  меняется (файл перезаписывается тем же содержимым), а одинаковые подряд идущие записи в журнале подавляются
  функцией `_log()`.

## Возможности

**1C_update_Platform**

- Определяет установленные 64-разрядные платформы в `C:\Program Files\1cv8` и выбирает две последние версии.
- Сохраняет исходный `techsys.dll` новой платформы: переименовывает его в имя второго файла `techsys` из прошлой
  версии (того, что с символом `_` в имени).
- Копирует `techsys.dll` из прошлой версии платформы в новую.
- Проверяет результат по размерам файлов и пишет итог в журнал.
- Если работает служба сервера 1С и её путь уже ссылается на новую версию платформы — добавляет флаг `-debug` в
  `ImagePath` (если его там нет) и перезапускает службу.

**1C_Web_update_Publication**

- Определяет публикации Apache: через WMI находит запущенные службы, в пути которых есть `Apache` или `httpd.exe`,
  и анализирует их `conf\httpd.conf`.
- Определяет публикации IIS: рекурсивно обходит `C:\inetpub\wwwroot` и анализирует `web.config`.
- Если публикация ссылается на предыдущую версию платформы, а новая версия уже установлена — переписывает
  версию в конфигурационном файле.
- Перед применением изменений проверяет, что DLL новой версии, на которую переключается публикация, действительно
  существует.
- Останавливает и заново запускает службу веб-сервера (`net stop` / `net start`).

**Общее для обеих программ**

- Работают по расписанию планировщика заданий Windows (прилагаются готовые `.bat` для регистрации).
- Требуют права администратора (`#RequireAdmin`).
- Ведут журнал рядом со скриптом (`<имя скрипта>.log`) с защитой от дубликатов подряд идущих записей.
- Не дают запуститься двум копиям одновременно: PID последних запусков хранится в `.ini`.
- Перехватывают критические ошибки AutoIt через UDF `OnAutoItErrorRegister`, передавая ей в качестве
  пользовательского обработчика имя `_MyErrorHandler` (в коде он прокомментирован как «игнорирование ошибок при
  помощи пустой `_MyErrorHandler`»). Самой функции `_MyErrorHandler` в скриптах нет, а вызов пользовательского
  колбэка в самой UDF закомментирован — фактическую работу выполняет внутренний обработчик UDF. В
  `1C_Web_update_Publication` регистрация выполняется всегда, в `1C_update_Platform` — только для
  скомпилированного `.exe` или `_stripped`-варианта (см. `If @Compiled or StringInStr(@ScriptName,'_stripped')`).

## Ключевые файлы

### `1C_update_Platform.au3`

| Элемент | Описание |
|---|---|
| `_getLastPlatform64()` | Возвращает массив полных путей к папкам внутри `C:\Program Files\1cv8`, отбирает те, в пути которых есть `\d+\.\d+\.\d+` (остальные папки игнорируются), и сортирует их по убыванию функцией `_VersionCompare`. Элемент `[0]` — самая свежая версия |
| Вставка `C:\Program Files\1cv8\9.9.99.9999` | Фиктивный «самый новый» путь. В режиме `$WorkRestart = False` он добавляется в начало массива, чтобы индекс `[1]` был самой новой реальной платформой, а `[2]` — предыдущей |
| Маска `techsys*dll` | Поиск файлов в папке `\bin` платформы (без подкаталогов, сортировка по имени). У старой платформы ожидается не менее двух таких файлов: `techsys.dll` и дополнительный файл с `_` в имени; у новой — не менее одного (`techsys.dll`) |
| `FileMove` + `FileCopy` | Сначала `FileMove` переименовывает `techsys.dll` новой платформы, давая ему имя второго файла `techsys` из старой платформы (так сохраняется исходный файл новой поставки). Затем `FileCopy` копирует `techsys.dll` из старой платформы в новую |
| Проверка `$succ` | Успех фиксируется, если размер скопированного файла совпадает с исходным и переименованный файл существует с отличающимся размером |
| Перебор служб | `1C:Enterprise 8.5 Server Agent (x86-64)` и `1C:Enterprise 8.3 Server Agent (x86-64)`. Через `sc.exe query` проверяется состояние `RUNNING` |
| Правка реестра | Читается `HKLM\SYSTEM\CurrentControlSet\Services\<служба>\ImagePath`. Если путь содержит новую версию платформы и в нём ещё нет `-debug`, флаг дописывается (`RegWrite`, тип `REG_EXPAND_SZ`) |
| Перезапуск | `sc.exe stop` → `Sleep(500)` → `sc.exe start` → `Sleep(5500)` → `net start`. Выполняется для **первой** подошедшей службы, после чего цикл прерывается (`ExitLoop`) |

### `1C_Web_update_Publication.au3`

| Элемент | Описание |
|---|---|
| `_getLastPlatformWeb64()` | Похожа на `_getLastPlatform64()`, но дополнительно отбирает только те версии, в которых есть `\bin\webinst.exe`. Сортировка — строковая, через `_ArraySort`, а не `_VersionCompare`, поэтому при номерах релизов разной длины порядок может не совпадать с числовым |
| `_GetServicesList()` | Получение списка запущенных служб через WMI (`Win32_Service WHERE Started = 'True'`) |
| `_getApachePublication()` | Среди запущенных служб ищет те, в пути которых есть `Apache` или `httpd.exe`, заменяет в пути `\bin\…` на `\conf\httpd.conf` и извлекает версию регулярным выражением `_1cws_module.*/(\d+\.\d+\.\d+[^/]*)/`. Имя службы берётся из WMI |
| `_getWebIISPublication()` | Рекурсивный обход `C:\inetpub\wwwroot` в поисках `web.config`, извлечение версии из атрибута `scriptProcessor`. Имя службы всегда записано как `W3SVC` |
| Перепубликация | Если публикация ссылается на `$aPlatfs[1]` (предыдущая версия), а не на `$aPlatfs[0]` (новая), версия в конфигурации заменяется на новую. Перед записью проверяется существование DLL из строки `_1cws_module "…"` |
| Перезапуск веб-сервера | Запись конфига → `net stop <служба>` → пауза 1 c → повторная запись конфига → `net start <служба>` → пауза 1 c → повторный `net start`. Каждый шаг логируется (успехом считается код возврата `0` от `net`) |
| `$WorkRestart` | В веб-скрипте установлено в `True`, поэтому изменения конфигов и рестарт служб **применяются по-настоящему**, а не «вхолостую» |
| `_log()` | Запись в журнал вида `<дата_время>\t<компьютер>\t<сообщение>`; повторные одинаковые записи отбрасываются |

**Общие и неиспользуемые функции**

В обоих скриптах есть общие вспомогательные функции. Часть из них в текущей логике **не вызывается** и оставлена
как заготовка: `_PathGetLast()` (выбор последних по дате папок/файлов), `_dr()` (преобразование даты вида
`20250928000000` в `YYYY/MM/DD HH:MM:SS`) и `_Trans()` (транслитерация кириллицы). Кроме того, в
`1C_update_Platform.au3` присутствуют определения функций веб-публикации (`_getApachePublication()`,
`_getWebIISPublication()`, `_GetServicesList()`), которые этим скриптом не используются — рабочими они являются
только в `1C_Web_update_Publication.au3`. `_PathSplitByRegExp()` определена в обоих скриптах, но вызывается
только в `1C_update_Platform.au3` — для выделения имени файла из пути.

Ещё одна особенность `1C_update_Platform.au3`: блок перезапуска служб (строки с `$aServices`) выполняется
**до** финальной проверки `$succ`, поэтому служба перезапускается независимо от того, успешно ли прошёл перенос
`techsys.dll`.

### `Планировщик-*.bat`

Выполняют `chcp 1251`, удаляют старое задание планировщика, создают новое (`schtasks /create /IT /RU "%USERNAME%"
/RL HIGHEST /SC MINUTE /mo 3` или `/mo 5`), запускающее `AutoIt3.exe` с соответствующим `_stripped.au3`-файлом из
текущего каталога, и сразу запускают его (`schtasks /run /i`). Имя задания совпадает с именем программы
(`1C_update_Platform` / `1C_Web_update_Publication`).

## Системные требования

- **ОС:** Windows x64. Конкретные редакции в коде не проверяются; ориентир — Windows Server, где разворачивается
  1С:Предприятие. Скрипты работают только с 64-разрядными платформами 1С из `C:\Program Files\1cv8`.
- **Платформа 1С:** установленные версии 1С:Предприятия 8.3/8.5 для Windows. Нужно **не менее двух установленных
  версий** — самая свежая и предыдущая:
  - если в `C:\Program Files\1cv8` нет ни одной подходящей папки версий, скрипт завершается с сообщением
    «Нет новых платформ»;
  - если установлена ровно одна версия, скрипт обращается к несуществующему элементу массива `$aPlatfs[2]` и
    аварийно завершается (подробнее — в разделе «Ограничения»).
- **Права:** администратор. Обе программы содержат директиву `#RequireAdmin` — для записи в `C:\Program Files`,
  изменения конфигурации веб-серверов, управления службами и правки `HKLM`. Задание планировщика регистрируется с
  `/RL HIGHEST`.
- **Веб-сервер (для `1C_Web_update_Publication`):** Apache HTTP Server (служба, в пути которой есть `Apache` или
  `httpd.exe`) и/или IIS с опубликованными базами в `C:\inetpub\wwwroot`.
- **AutoIt:** для запуска `_stripped.au3`-файлов достаточно переносного интерпретатора `AutoIt3.exe`, который уже
  входит в состав проекта (в файле указана версия 3.3.14.1). Для самостоятельной сборки и компиляции потребуется
  полный AutoIt v3 вместе с SciTE4AutoIt3 и AutoIt3Wrapper (см. раздел «Сборка»).

## Установка и запуск

1. Скопируйте весь каталог проекта на сервер 1С (путь может быть любым, `.bat`-файлы используют относительные
   пути через `%~dp0`).
2. Убедитесь, что установлено не менее двух версий платформы 1С и что в предыдущей версии уже выполнена
   ваша модификация `techsys.dll` (то есть в `\bin` есть и `techsys.dll`, и файл вида `techsys_*.dll`).
3. Запустите от имени администратора:
   - `Планировщик-1C_update_Platform.bat` — регистрирует задание, выполняющееся каждые 3 минуты;
   - `Планировщик-1C_Web_update_Publication.bat` — каждые 5 минут.
4. Проверьте, что задание создано и отработало:

   ```bat
   schtasks /query /tn "1C_update_Platform" /v /fo list
   ```

5. Посмотрите журнал рядом со скриптом — `1C_update_Platform.log` / `1C_Web_update_Publication.log`.

**Запуск вручную** (без планировщика):

```bat
AutoIt3.exe "1C_update_Platform_stripped.au3"
AutoIt3.exe "1C_Web_update_Publication_stripped.au3"
```

или запуск готовых `1C_update_Platform.exe` / `1C_Web_update_Publication.exe` от имени администратора.

## Пример использования

Типовой порядок действий администратора при выходе нового релиза платформы:

1. Установите новую версию платформы 1С обычным способом — она появится в `C:\Program Files\1cv8\<новая версия>`.
2. Убедитесь, что в **предыдущей** версии применена ваша доработка `techsys.dll`: в её каталоге `\bin` должны
   лежать и `techsys.dll`, и дополнительный файл `techsys_*.dll`. Именно этот `techsys.dll` программа перенесёт в
   новую версию. Если доработка не применена — `1C_update_Platform` завершится, ничего не сделав.
3. Больше ничего делать не нужно. Дождитесь срабатывания заданий планировщика (до 3 минут для
   `1C_update_Platform` и до 5 минут для `1C_Web_update_Publication`) или запустите программы вручную.
4. Проверьте по журналу, что `techsys.dll` перенесён, а публикации переключились на новую версию.

## Пример сценария работы

Ниже описано, что именно делают программы в соответствии с кодом. В примере использованы номер версии
`8.3.27.1786` и имя `wsap24.dll`, которые встречаются в комментариях и регулярных выражениях исходников;
номер `8.3.27.1801` и имя `techsys_xxx.dll` — условные обозначения новой версии и второго файла `techsys`
(имя берётся из реального файла на вашем сервере).

### Сценарий 1. `1C_update_Platform` (восстановление techsys.dll)

**Исходное состояние.** На сервере установлены две версии: `C:\Program Files\1cv8\8.3.27.1786\` (в её `\bin`
лежат два файла — `techsys.dll` и `techsys_xxx.dll`, именно такой состав и требуется программе) и новая
`C:\Program Files\1cv8\8.3.27.1801\` (в `\bin` только исходный `techsys.dll` из поставки).

1. При запуске скрипта `_closeLastProc()` проверяет по `.ini`, не висит ли предыдущая копия, и завершает её.
2. `_getLastPlatform64()` возвращает массив версий, отсортированный по убыванию: `[8.3.27.1801, 8.3.27.1786]`.
   Поскольку `$WorkRestart = False`, в начало добавляется фиктивный `9.9.99.9999`, и массив принимает вид
   `[9.9.99.9999, 8.3.27.1801, 8.3.27.1786]`. Переменная `$newVer` вычисляется из первого элемента массива, то
   есть из фиктивного пути, но дальше в этом скрипте **не используется** — рабочая версия берётся из пути выбранной
   платформы (см. шаг 8).
3. Версия для обработки — `$aPlatfs[1]` (новая, `8.3.27.1801`), источник — `$aPlatfs[2]` (предыдущая,
   `8.3.27.1786`).
4. В `C:\Program Files\1cv8\8.3.27.1786\bin` по маске `techsys*dll` находятся два файла; в имени второго
   присутствует `_`. Если файлов меньше двух или у второго нет `_` — скрипт завершается, записав в журнал
   «нет старого techsys …», и больше ничего не делает. Если в новой версии нет ни одного файла `techsys*dll` —
   «нет нового techsys …».
5. `FileMove` переименовывает `…\8.3.27.1801\bin\techsys.dll` в `…\8.3.27.1801\bin\techsys_xxx.dll` — имя
   берётся из второго файла старой платформы. Так исходный файл новой поставки сохраняется.
6. `FileCopy` копирует `…\8.3.27.1786\bin\techsys.dll` в `…\8.3.27.1801\bin\techsys.dll` — это и есть перенос
   вашего `techsys.dll` в новую версию.
7. Перебираются службы `1C:Enterprise 8.5 Server Agent (x86-64)` и `1C:Enterprise 8.3 Server Agent (x86-64)`.
   Версия для сравнения берётся из `$PlatNewVer` — последнего компонента пути `$aPlatfs[$NewNum]`, то есть
   `8.3.27.1801`. Если служба в состоянии `RUNNING` и её `ImagePath` уже содержит `8.3.27.1801`, то при
   отсутствии `-debug` флаг дописывается в реестр, а служба перезапускается (`sc.exe stop` → `sc.exe start` →
   `net start`). Если `ImagePath` ссылается на другую версию — служба пропускается. Этот шаг выполняется даже
   в случае неудачи на шагах 5–6.
8. Проверка результата: размер нового `techsys.dll` совпал с размером исходного, а переименованный файл
   существует и размер у него другой — `$succ = 2`. В журнал пишется `успешно techsys_xxx.dll`, после чего
   скрипт завершается (`_quit`).
9. При следующем запуске (через 3 минуты) шаги 5–6 повторятся: `FileMove` перезапишет `techsys_xxx.dll` тем же
   содержимым, а `FileCopy` — `techsys.dll`. Состав файлов не изменится, `$succ` снова будет равен `2`, и в журнал
   снова попадёт строка `успешно techsys_xxx.dll` (если она совпадает с предыдущей записью, `_log()` её
   отбросит).

### Сценарий 2. `1C_Web_update_Publication` (перепубликация на веб-сервере)

**Исходное состояние.** В `httpd.conf` Apache есть строка вида
`LoadModule _1cws_module "C:/Program Files/1cv8/8.3.27.1786/bin/wsap24.dll"`, установлена новая платформа
`8.3.27.1801` с `\bin\webinst.exe`.

1. `_getLastPlatformWeb64()` возвращает `[8.3.27.1801, 8.3.27.1786]` (обе версии существуют и содержат
   `bin\webinst.exe`). Здесь вставка фиктивной версии **не выполняется**, так как `$WorkRestart = True`.
2. Через WMI отбираются все запущенные службы; среди них ищутся те, чей путь содержит `Apache` или `httpd.exe`.
   Для каждой такой службы путь вида `…\bin\httpd.exe` преобразуется в `…\conf\httpd.conf`, конфигурация
   читается и из строки `_1cws_module …/8.3.27.1786/…` извлекается версия публикации.
3. Публикация указывает на `8.3.27.1786` — это `$aPlatfs[1]`, а не `$aPlatfs[0]` (`8.3.27.1801`). Значит,
   требуется перепубликация. В журнал пишется: «Начинаем публикацию Apache с версии 8.3.27.1786 на
   C:\Program Files\1cv8\8.3.27.1801 для файла <путь к httpd.conf>».
4. В конфигурации версия заменяется на новую: `…/8.3.27.1801/…`.
5. Из получившейся строки извлекается путь к DLL (`_1cws_module "…"`), и проверяется, что файл
   `C:\Program Files\1cv8\8.3.27.1801\bin\wsap24.dll` существует. Если его нет — перепубликация отменяется с
   записью в журнал «Нет нужного файла …».
6. Конфигурационный файл перезаписывается, служба Apache перезапускается: запись конфига → `net stop` →
   пауза 1 с → повторная запись конфига → `net start` → пауза 1 с → ещё один `net start`. Каждый шаг пишется в
   журнал.
7. Затем аналогично обрабатываются публикации IIS: обход `C:\inetpub\wwwroot`, замена версии в атрибуте
   `scriptProcessor` файлов `web.config` и перезапуск службы `W3SVC`.
8. При следующем запуске (через 5 минут) публикация уже ссылается на `$aPlatfs[0]` — в журнал пишется «Уже стоит
   новая версия …», и изменения не вносятся.

## Настройка конфигурации

Отдельного конфигурационного файла с параметрами у проекта нет — все настройки зашиты в исходный текст скриптов.
Если потребуется адаптация под свой сервер, правятся следующие места (только в `.au3`, после чего нужен
пересбор `_stripped`-версии или перекомпиляция):

| Что изменить | Где | Значение по умолчанию |
|---|---|---|
| Каталог установки платформ 1С | `_getLastPlatform64()`, `_getLastPlatformWeb64()` | `C:\Program Files\1cv8` |
| Каталог публикаций IIS | `_getWebIISPublication()` | `C:\inetpub\wwwroot` |
| Имена служб сервера 1С | `Global $aServices[2]` | `1C:Enterprise 8.5 Server Agent (x86-64)`, `1C:Enterprise 8.3 Server Agent (x86-64)` |
| Имя службы IIS для перезапуска | `_getWebIISPublication()` (записано в коде) | `W3SVC` |
| Имя службы Apache | определяется автоматически из WMI | — |
| Добавляемый флаг запуска сервера 1С | блок правки `ImagePath` | `-debug` |
| Маска файлов techsys | вызовы `_FileListToArrayRec` | `techsys*dll` |
| Интервал запуска заданий | `Планировщик-*.bat` | 3 минуты и 5 минут |
| Учётная запись задания | `Планировщик-*.bat`, ключ `/RU` | `%USERNAME%` |

`.ini`-файлы (`1C_update_Platform.ini`, `1C_Web_update_Publication_stripped.ini`) — это **не настройки**: в них
хранятся только `$last_pid` и `$last_pid2` для защиты от параллельных запусков. Они создаются автоматически при
первом запуске и перезаписываются при каждом старте программы.

> **Предупреждение.** В исходных текстах в комментарии встречается пример пути конкретного пользователя
> (`C:\Users\...\AppData\Local\Programs\1cv8_x64\8.3.27.1786\`) — это пример из разработки, в логику программы он
> не используется. Файл `opencode.json` также содержит абсолютные пути данного компьютера и поэтому исключён из
> Git. Перед публикацией собственных форков проверяйте, чтобы в коммит не попали личные пути, имена
> пользователей, пароли и токены.

## Сборка проекта в EXE

Сборкой управляют директивы AutoIt3Wrapper в заголовке каждого скрипта:

```autoit
#Region ;**** Directives created by AutoIt3Wrapper_GUI ****
#AutoIt3Wrapper_Run_Au3Stripper=y
#Au3Stripper_Parameters=/so /rsln
#EndRegion
```

1. Установите AutoIt v3 и SciTE4AutoIt3 (входит в полный дистрибутив AutoIt).
2. Откройте `1C_update_Platform.au3` (или `1C_Web_update_Publication.au3`) в SciTE.
3. Выполните `Tools → Au3Stripper` (создаст `*_stripped.au3`, объединив все `#include` в один файл — именно его
   запускает планировщик), затем `Tools → Compile` (соберёт `.exe`).
   Альтернативный вариант — компиляция сразу по `.au3`: AutoIt3Wrapper выполнит Au3Stripper сам благодаря
   директиве `#AutoIt3Wrapper_Run_Au3Stripper=y`.
4. Готовые `.exe` появятся в каталоге скрипта. Версия ресурса и сведения о продукте в них не задаются —
   соответствующие директивы в проекте отсутствуют, поэтому используются значения AutoIt по умолчанию.

Параметры `/so /rsln` — режимы Au3Stripper: `/so` (strip only — из результата убираются комментарии и лишнее
форматирование, функции и переменные не переименовываются), `/rsln` (renumber line numbers — номера строк в
сообщениях об ошибках приводятся в соответствие со строками исходного `.au3`, что и видно по поставляемым
`*_stripped.au3`).

**Сборка из командной строки:**

```bat
AutoIt3Wrapper.exe /in "1C_update_Platform.au3"
AutoIt3Wrapper.exe /in "1C_Web_update_Publication.au3"
```

> Версия программы в ресурсах собираемого `.exe` явно не задаётся (директивы `#AutoIt3Wrapper_Res_FileVersion` и
> `#AutoIt3Wrapper_Res_ProductVersion` отсутствуют). Нумерация версий проекта ведётся только в `CHANGELOG.md`.

## Ограничения и известные проблемы

- **Только x64.** Учитываются только платформы в `C:\Program Files\1cv8`; 32-разрядные установки из
  `C:\Program Files (x86)\1cv8` не обрабатываются.
- **Жёсткие пути.** `C:\Program Files\1cv8` и `C:\inetpub\wwwroot` прописаны в коде и не вынесены в настройки.
- **Требуется «эталон» techsys.** Если в предыдущей версии платформы нет дополнительного файла вида
  `techsys_*.dll`, программа завершается, ничего не сделав. Сам доработанный `techsys.dll` в репозиторий не
  входит — проект его не распространяет.
- **Только две последние версии.** Источником всегда служит версия на позиции `$aPlatfs[2]` после вставки
  фиктивного элемента, то есть версия, непосредственно предшествующая самой свежей. Если «эталоном» должна быть
  более старая версия, это потребует правки кода.
- **Контроль качества только по размеру.** Успех переноса `techsys.dll` проверяется совпадением размеров файлов,
  проверок контрольных сумм, цифровой подписи или совместимости версии DLL нет. При неудаче скрипт не
  прекращает работу: он просто не запишет в журнал «успешно …», а службу 1С всё равно перезапустит.
- **Аварийное завершение, если установлена ровно одна версия платформы.** Сообщение «Нет новых платформ»
  выдаётся только когда в `C:\Program Files\1cv8` нет ни одной подходящей папки (`If UBound($aPlatfs) < 2`).
  Если же версия одна, после вставки фиктивного `9.9.99.9999` массив состоит из двух элементов, проверка
  проходит, и скрипт обращается к несуществующему элементу `$aPlatfs[2]` — это критическая ошибка AutoIt
  («Array variable has incorrect number of subscripts»), после которой скрипт завершается.
- **`1C_Web_update_Publication` перезапускает только запущенные службы.** Поиск служб ведётся через WMI с фильтром
  `Started = 'True'`; остановленные веб-серверы не обнаруживаются.
- **Опубликованные базы ищутся по конфигурационным файлам**, а не обращением к механизму публикации 1С
  (`webinst.exe`). Для Apache анализируется только тот `httpd.conf`, который расположен рядом с `\bin` службы.
- **Нет отката.** При ошибке записи конфигурации резервная копия не создаётся; перед правкой `httpd.conf` /
  `web.config` рекомендуется иметь собственный бэкап.
- **Имена `.ini`-файлов зависят от способа запуска.** Поскольку планировщик запускает `_stripped.au3`, веб-скрипт
  использует `1C_Web_update_Publication_stripped.ini` (а не `1C_Web_update_Publication.ini`). Запуск
  скомпилированного `.exe` создаст собственный `.ini` с именем исполняемого файла.
- **Накопительный лог во временный файл.** Веб-скрипт в конце создаёт во временном каталоге `.txt` и записывает
  в него накопленный лог, но его открытие (`ShellExecute`) закомментировано. Основной журнал — `.log` рядом со
  скриптом. В `1C_update_Platform.au3` аналогичный блок расположен после `Exit` и поэтому недостижим.
- **Запуск `.au3` напрямую, без компиляции.** В `1C_update_Platform.au3` обработчик ошибок регистрируется только
  для скомпилированного или `_stripped`-варианта (`If @Compiled or StringInStr(@ScriptName,'_stripped')`).
  Поэтому при запуске исходного `.au3` напрямую любая критическая ошибка AutoIt приведёт к появлению
  стандартного окна с сообщением. Используйте `_stripped`-вариант или `.exe`, как описано в «Установке и запуске».
- **Разная сортировка версий в двух скриптах.** `1C_update_Platform` сортирует версии функцией `_VersionCompare`
  (числовое сравнение), а `1C_Web_update_Publication` — строковой `_ArraySort`. Для номеров релизов разной длины
  (например, `8.3.24.999` и `8.3.24.1000`) строковый порядок может не совпадать с числовым.
- **Много отладочного вывода.** В коде остались вызовы `ConsoleWrite('@@ Debug …')`; они видны только при запуске
  с консолью и не влияют на работу планировщика.
- **В проекте есть закомментированный, не реализованный функционал:** FTP-клиент (`FTPEx.au3`, переменные
  `$ftpserver`, `$ftplogin`, `$ftppassword`), `Inet.au3` и отправка лога внешней функции `_SendLog`. Они не
  используются и результатов не дают. (`Crypt.au3`, тоже закомментированная в основных скриптах, в сборку всё же
  попадает — её подключает UDF `OnAutoItErrorRegister` для шифрования исходника.)
- **Архив `1С_upd.7z`** в корне проекта не имеет описания; назначение и содержимое не указаны.

## Безопасность и обрабатываемые данные

**Что программа делает с системой (требует прав администратора):**

- изменяет файлы в `C:\Program Files\1cv8\<версия>\bin` (перенос/копирование `techsys*.dll`);
- изменяет `httpd.conf` веб-сервера Apache и `web.config` в дереве `C:\inetpub\wwwroot`;
- изменяет реестр `HKLM\SYSTEM\CurrentControlSet\Services\…\ImagePath` (добавляет флаг `-debug` в параметры
  запуска службы сервера 1С);
- останавливает и запускает системные службы через `sc.exe` и `net start/stop`.

**Какие данные обрабатываются:**

- Пути к установленным версиям платформы 1С и файлы `techsys*.dll` из их каталогов `bin`.
- Содержимое конфигурационных файлов веб-сервера и пути к DLL модуля `_1cws_module` / `scriptProcessor`.
- Имена и пути запущенных служб (через WMI), имена компьютеров (`@ComputerName`) попадают в журнал.
- PID собственных процессов в `.ini`-файлах.

**Что проект НЕ собирает и НЕ хранит:** пароли, токены, учётные данные пользователей 1С, SQL-пароли, содержимое
баз данных. Файлов `.env` и секретов в проекте нет; закомментированные переменные FTP-подключения значения не
получают и никуда не передаются.

**Меры предосторожности:**

1. Перед использованием в рабочей среде проверьте работу на тестовом сервере. Подмена `techsys.dll` и
   автоматический рестарт служб — операции, влияющие на доступность баз.
2. Делайте резервные копии `httpd.conf`, `web.config` и папок `bin` платформ перед тем, как разрешите скриптам
   вносить изменения.
3. Убедитесь, что задание планировщика выполняется от имени учётной записи с минимально необходимыми правами
   (администратор требуется обязательно — см. `#RequireAdmin`).
4. Не коммитьте в публичный репозиторий файл `.ini` с PID, `.log`-файлы и `opencode.json` — они уже исключены
   через `.gitignore`.
5. Переносимый `techsys.dll` содержит ваши изменения платформы 1С. Его распространение и способ внесения
   изменений могут регулироваться лицензионным соглашением 1С; проект сам по себе этот файл не содержит и не
   распространяет.
